# 悬浮球语音唤醒

用一个小悬浮球替代「后台常驻监听唤醒词」，作为随时说话的入口。

---

## 为什么换掉后台唤醒

原先的实现是一个前台服务**一直占用麦克风监听唤醒词**，问题：

| 问题 | 说明 |
| --- | --- |
| 耗电 | 麦克风常开，系统无法休眠 |
| 被限制 | 各家 ROM 会杀后台服务，唤醒时灵时不灵 |
| 不确定 | 用户不知道唤醒词有没有被听到，喊了没反应很困惑 |
| 权限 | 需要常驻麦克风权限，隐私上也不舒服 |

悬浮球只是**一个可点的小窗口**，代价低得多，交互也明确：
点一下就开始说话，不用猜。

---

## 交互设计

```
     完整状态                 拖到边缘松手            收起状态
    ┌────────┐                                      ┌───┐
    │  🎤   │  ─────────拖动─────────►              │ 🎤│ ← 露出约一半
    └────────┘                                      └───┘
    52 dp                                            26 dp
```

| 操作 | 行为 |
| --- | --- |
| 点一下 | 开始说话（识别结果送进 Fairy） |
| 拖动 | 移动位置，跟手 |
| 拖到左/右边缘松手 | 自动滑出屏外一半，只露半边 |
| 收起状态下点一下 | 展开回完整大小 |
| 收起状态下拖动 | 恢复完整大小并跟随手指 |

### 尺寸上的取舍

- **完整 52dp**：比系统返回手势条醒目，又不挡内容
  （参考：iOS AssistiveTouch 约 56dp）
- **收起后露 26dp**：正好一半，满足「隐藏成半个」，
  但**始终露出**，所以永远不会「看不见」

这两条约束已固化成自动检查（`tools/check-floating-ball.py`），
避免以后改坏了。

## 使用步骤

**1. 授予悬浮窗权限**

首次开启时，Fairy 会跳转到系统的「显示在其他应用上层」页面。
找到 **Fairy** 并允许。

> 这是 Android 的「特殊权限」，无法在应用内弹窗申请，只能这样跳转。
> 部分 ROM 路径为：设置 → 应用管理 → Fairy → 显示在其他应用上层。

**2. 打开开关**

设置 → **悬浮球（语音唤醒）** → 打开「显示悬浮球」。

授权后会自动开启，不用再点一次。

**3. 使用**

小球出现在屏幕上（默认在右侧偏下，拇指容易够到的位置）。
点一下就说话，说完的结果会送进 Fairy 的输入框。

## 技术实现

| 部分 | 文件 | 职责 |
| --- | --- | --- |
| 悬浮窗 | `FloatingBallService.java` | 绘制小球、拖动、吸附、收起动画 |
| 桥接 | `MainActivity` 的 `floatingBall*` | 开关、状态查询、权限跳转 |
| 界面 | `js/floating-ball.js` | 设置开关、权限引导、接收点击 |

### 几个关键点

**为什么不用前台服务**（重要，曾因此崩溃）

最初用 `startForegroundService()` + `startForeground()` 来做保活，
在 Xiaomi / Android 15 上直接崩溃：

```
ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground()
```

原因是系统要求 `startForegroundService()` 后 **5 秒内**调用 `startForeground()`，
而悬浮球需要向 `WindowManager` 注册窗口，这一步在部分 ROM 上可能慢或失败。

更糟的是：失败分支里调用 `stopSelf()` 同样算「启动了但没进前台」，照样崩。

**现在改为普通 Service + 常驻通知**：

| | 前台服务 | 普通服务（现在） |
| --- | --- | --- |
| 5 秒限制 | 有（已崩） | 无 |
| Android 14+ 类型校验 | 严格，dataSync 还需额外权限 | 不涉及 |
| 存活率 | 高 | 中（有常驻通知 + `START_STICKY`） |

取舍理由：悬浮球是「可选的便利功能」，被系统回收后用户重新打开开关即可，代价很低；
而崩溃是致命的。所以优先保证绝不崩。

**为什么不能在 Service 里用 `getDisplay()`**（第二次崩溃的原因）

```
UnsupportedOperationException: Tried to obtain display from a Context
not associated with one.
```

`Service` 属于**后台实体**，不是 visual Context，没有关联的 `Display`。
在 Service 中调用 `Context#getDisplay()` 必然抛异常。

正确做法（按优先级降级，任何一层失败都继续往下降）：

1. **API 30+**：`WindowManager#getCurrentWindowMetrics()`（官方推荐）
2. `WindowManager#getDefaultDisplay()`（各版本可用，API 30+ 已废弃）
3. 兜底：`Resources#getDisplayMetrics()`（可能拿到可用区域，但不会崩）

最后还给屏幕尺寸设了默认值（1080×1920），避免 0 导致窗口无法创建。

**为什么不能运行时申请权限**
`SYSTEM_ALERT_WINDOW` 属于特殊权限，`requestPermissions` 对它无效，
只能 `ACTION_MANAGE_OVERLAY_PERMISSION` 跳设置。

**点击后怎么让 Fairy 收到**
小球被点击 → 服务置一个待处理标志 → 拉起 `MainActivity`（`singleTop`）
→ 页面通过 `window.__fairyVoice.onFloatingBallTap()` 进入语音输入。

冷启动时页面还没就绪，所以带重试（最多约 8 秒）。

**开启失败时为什么勾选不会弹回**
`startService()` 是异步的，「调用成功」不等于「服务活着」。
早期版本 400ms 后读状态发现没起来，就把用户刚勾的开关打回去，
**而且不给任何原因** —— 用户完全不知道发生了什么。

现在 `floatingBallStart()` 会等待最多 1.2 秒确认结果，返回：

| 返回值 | 含义 |
| --- | --- |
| `"1"` | 已开启且服务确认存活 |
| `"noperm"` | 缺悬浮窗权限 |
| `"failed:<原因>"` | 服务起来了但窗口没建成功 |
| `"error:<原因>"` | 调用本身异常 |

失败时**保留勾选**并把原因写进状态区，便于重试或截图反馈。

**转屏处理**
`onConfigurationChanged` 里重新计算屏幕尺寸并吸附，
否则横屏后小球可能落在屏幕外。

## 常见问题

**小球不见了**
检查通知栏是否有「Fairy 悬浮球已开启」。没有的话说明服务被系统回收了，
回设置里重新打开开关即可（这是普通服务的正常代价，见上文取舍说明）。

**开了开关但没看到小球**
多半是权限没给。设置里会显示「还差一步：需要…权限」。

**小球挡住内容**
拖到左或右边缘松手，它会收起成半个。

**不想要了**
关掉「显示悬浮球」开关即可，通知也会消失。

**耗电吗**
不会明显耗电。悬浮球不会占用麦克风，只是在屏幕上画一个小窗口；
麦克风只在点击后说话的那几秒被使用。
